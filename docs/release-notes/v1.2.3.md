A release you can check for yourself: the published zips now match a build of the same commit on your own machine. Plus a fix to the install command the popup prints, and Tailscale 1.102.3 underneath.

No re-registration is needed — the native messaging host name has not changed since v1.2.1. Upgrading still means replacing the backend binary, since it is copied into your browser's configuration directory at install time:

```
go run github.com/iazat/ts-browser-ext@latest --install=C<your-extension-id>   # Chrome
go run github.com/iazat/ts-browser-ext@latest --install=F                      # Firefox
```

Building the backend now needs Go 1.26.6 or newer, which is what Tailscale 1.102.3 requires. A `go` command with its default toolchain setting fetches that for you; one pinned with `GOTOOLCHAIN=local` reports the version instead of building.

## The published zip did not match your own build of it

v1.2.1 said an asset could be checked against a local build. It could not. The v1.2.2 zip published from CI and a build of that exact commit on another machine came out the same size, held byte-identical files, and shared no checksum: 165082 of 166046 bytes differed.

`zip -r` adds entries in the order the filesystem hands them out. That order is a property of the machine, not of the contents, so two correct builds packed the same files into different places in the archive. Flattening the timestamps, which is all v1.2.2 did, never touched it. The check that was being run — build twice here, compare — is precisely the one that cannot see it, because one machine walks its own directory the same way every time.

The file list is sorted before it reaches zip now, and the packaging script fails rather than publishing an archive whose entries came out in some other order. Verify a download against your own build:

```sh
script/package.sh                       # from a clone checked out at the tag
shasum -a 256 dist/ts-browser-ext-chrome-v1.2.3.zip
```

## The install command could name the wrong browser

The command the popup prints carries a byte saying which browser to register the native host for, and both extensions worked that byte out at runtime. Neither signal survives: Chrome defines the `browser` global these days, and the Chrome copy read a user agent, which anything on the machine can rewrite.

A wrong byte fails quietly. The command registers the host under the other browser's name, the install reports success, and the popup goes on asking you to install a backend that is already sitting on disk. The two extensions are separate copies that cannot move between browsers, so each one now simply states which it is.

## Tailscale 1.102.3

Two of its fixes land in the code this backend runs on every page load, since the whole browser profile goes through this process's userspace network stack: netstack refuses to forward 4via6 traffic to host-scoped targets, and bare names no longer resolve when MagicDNS is turned off.

## Known limitations

- **Firefox has still not been run live.** Its test suite passes and it is exercised against a mocked browser API on every commit, but nobody has loaded it through `about:debugging`.
- **Losing the backend still hands the browser a direct connection.** When the native messaging host goes away, the extension resets the browser proxy to direct rather than to a dead port — about a second per reconnect. Making that fail closed would mean pages stop loading entirely whenever the backend dies, and has not been done.
- **Windows cannot register the native host.** The binary builds, but there is no registry install path yet.
