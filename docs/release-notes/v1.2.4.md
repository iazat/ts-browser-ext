The release for the hang. Six fixes, all in how the extension and its backend survive each other, and none needing re-registration — the native messaging host name is unchanged since v1.2.1. Upgrading still means replacing the backend binary:

```
go run github.com/iazat/ts-browser-ext@latest --install=C<your-extension-id>   # Chrome
go run github.com/iazat/ts-browser-ext@latest --install=F                      # Firefox
```

## The extension hung after its backend restarted

Every native host is a fresh process. It has to be sent `init` — the profile id that names its state directory — before it starts tsnet, and the extension keeps a flag so `init` is sent exactly once. That flag survived the host dying. Whatever brought the host down (a command that failed, see below; the browser suspending it; a crash), its replacement was connected to, pointed at, and never told to start. It reported `NoState` for the rest of the browser session: the popup read "Connecting…", the exit node picker never appeared, and every page failed with `no tsnet.Server`. Reloading the extension was the only way out.

The Firefox copy had a second problem in the same place. It read the disconnect reason from `runtime.lastError`, which is Chrome's channel and is empty in Firefox's promise-based API — so a host that crashed looked like a clean disconnect, and under the old rule of only reconnecting on an error, Firefox never reconnected at all.

Both copies now reset the flag when the host goes away, reconnect whether or not the browser attached a reason, and back off between attempts (one second, doubling to thirty) rather than trying every second forever against a host that is not installed. The popup says "Reconnecting to the backend…" for a host that answered earlier and then went away, and keeps the install command for one that never has — with the browser's reason next to it, since "not found" and "exited" want different fixes. A backend that fails to start says why in the popup instead of only in the console.

## One failed command killed the whole proxy

The backend's message loop exited on any handler error, and exiting it exits the process, which is the proxy the browser is pointed at. Two of those errors were easy to hit: an `up` that arrived before `init` had finished — the toggle clicked in the first second — and an `EditPrefs` that missed its five-second deadline because the backend was busy applying a netmap. Either one took the whole browser offline for the seconds it took the extension to notice and start a replacement — which, per the previous section, it then failed to initialise.

A failed command is now reported to the extension (a `cmdError` message, logged) and the loop carries on. The LocalAPI deadline is ten seconds, and it is no longer held under the lock that every browser connection takes, so a slow call stalls nothing but itself.

## Concurrent replies corrupted the native messaging stream

Each reply is a four-byte length followed by JSON, and the backend writes them from several goroutines: the reader answering a command, the IPN bus watcher, the management page's handlers. The length was staged in a field shared with the reader and written with a separate call from the body. Two replies at once could put one message's length in front of the other's body, and a status arriving while the reader was parsing a command's length could change the length under it.

What the browser does with a frame that does not match is either drop the connection or wait for bytes that are never coming. The second is the one that looks like a hang: the popup stops updating, the toggle does nothing, and nothing in any log says why. Each frame is now built in its own buffer and written with one call under the lock, and a test sends 1,600 replies from 32 goroutines and checks every frame parses.

## A lagging watcher stopped the backend for good

Tailscale 1.102 closes an IPN bus watcher that falls 128 notifications behind, and this backend's watcher handled each notification by making two LocalAPI calls and writing to the browser before reading the next — slow enough on a busy tailnet. Once closed it was never reopened: the status carried "WatchIPNBus stopped" until the browser was restarted, the picker vanished and the toggle looked broken, with the tailnet in fact fine.

The watcher now only records what it is told and hands the status off to a goroutine of its own, which folds a burst of notifications into one status message. If the subscription ends anyway, it resubscribes with backoff; the initial state, netmap and preferences come again, so nothing is lost but the gap.

## A tab left on the management page could start the wrong node

`tsnet.Server.LocalClient` starts the server if it is not running, and the management page's handlers called it directly. Before `init` arrives the hostname and state directory are not set, so a request landing in that window brought up a node under a default directory with a default name — and `init`, a moment later, failed with "already running". The page refreshes itself every five seconds, and a tab left on it is restored at browser start, so the window was easy to land in. Its handlers now answer 503 until `init` has started tsnet, and the page's next refresh gets the real thing.

## Pages loaded right after startup failed instead of waiting

The browser is pointed at the proxy the moment its port is known, before `init` is even received, and a page loaded in the next seconds failed outright — `no tsnet.Server`, then `not routing yet`. Chrome renders those as a broken proxy. Dials now wait for the backend, up to twenty seconds, so those pages load a moment late instead. The wait is bounded so a backend that never gets there — no network, an expired login — still fails loudly.

In the other direction, a CONNECT to an exit node that had gone quiet had no deadline the browser would act on: the userspace stack retries the SYN for a long time, and the tab spins. CONNECT dials now carry a thirty-second deadline of their own.

## The exit node reset to None on every restart

tsnet starts the backend with a fresh set of preferences — hostname, WantRunning, the control URL — and Tailscale takes that as the whole set, replacing what was stored. The exit node went with it. Every restart of the backend, which is every browser start and every reload of the extension, put the picker back to None; and until this release the picker did not even get that far, because the restart hung the extension first. With the restart working, the reset was the next thing to notice.

It is not only a picker problem: with no exit node configured, the proxy lets traffic leave through this machine, which is exactly what selecting one was meant to prevent. The choice is now written beside the profile's state whenever it is made, from the popup or the management page, and put back right after the backend starts — before the IPN bus watcher subscribes, so the first preferences the proxy sees already name the node and it waits rather than dialling direct. Clearing the exit node is remembered the same way.

## Also
- The exit node pickers, in the popup and on the management page, are rebuilt only when their contents change and never while the user is in them. Replacing the options under an open menu made the browser commit whatever sat at the clicked position when the menu closed — None — and send it to the backend as a request to stop using the exit node.
- The backend logs to `tailscale-browser-ext/backend.log` under your config directory (`~/Library/Application Support` on macOS, `~/.config` on Linux), truncated at every start and capped at 20 MB. Under the browser its stderr went nowhere; now a question like "who cleared the exit node" has an answer. `/api/data` on the management page reports the live and saved exit node, the backend's pid and the log path.
- `npm run test:e2e` loads the real extension into a real Chromium, kills the backend, and checks the extension recovers on its own. A build of the previous release fails it on exactly the points fixed here.

- `init` runs off the reader goroutine. Starting tsnet is the one thing that takes seconds, and it ran on the goroutine that reads the browser's commands while holding the lock every proxy connection takes; had it hung, the process would not have noticed the browser closing its stdin.
- The backend closes tsnet on exit rather than dying with it open, so a replacement process does not find the state directory mid-write.
- The extension registers `runtime.onStartup` and `runtime.onInstalled`, so it is running — and re-pointing the browser at a live proxy — at browser start, when the proxy setting from the previous session still points at a port nothing listens on.
- The popup builds the install prompt from text rather than markup.

## Known limitations

- **Firefox has still not been run live.** Its test suite passes and it is exercised against a mocked browser API on every commit, but nobody has loaded it through `about:debugging`.
- **Losing the backend still hands the browser a direct connection** while it reconnects, as before.
- **Windows cannot register the native host.** The binary builds, but there is no registry install path yet.
