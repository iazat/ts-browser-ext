One bug, in four places: a Mac that went to sleep woke up with the extension dead, and it stayed dead until something happened to poke it — usually the user, opening the popup to find out why nothing loaded.

Upgrading needs both halves this time. The extension gains two permissions, so reload it; the backend changed too, so run the install command again — it copies the binary into your browser's configuration directory, and the old copy stays there until it does:

```
go run github.com/iazat/ts-browser-ext@latest --install=C<your-extension-id>   # Chrome
go run github.com/iazat/ts-browser-ext@latest --install=F                      # Firefox
```

No re-registration is needed — the native messaging host name has not changed since v1.2.1.

## A sleeping Mac left the extension dead

Sleep takes the whole chain down. The browser suspends, Chrome discards the service worker the extension runs in, and the native backend — a child process holding the messaging port — dies with it. That much is normal. What kept it down was four separate things, each enough on its own:

**Only one kind of disconnect was retried.** A host that exits by itself reports no `runtime.lastError`, and that is exactly the disconnect a sleeping machine produces; the retry ran only for the other kind. Even then it was a `setTimeout`, which does not survive the worker being discarded. There is a backoff now, from a second out to thirty, plus a one-minute alarm and an idle listener — both held by the browser, which starts the worker again to deliver them. Opening the popup retries at once rather than sitting out a delay while someone stares at it.

**The backend that did answer was never initialised.** The flag saying "this host has been told to start Tailscale" outlived the port that had earned it. The replacement is a new process with no tailnet in it, so it was never told: the browser was pointed at a proxy with nothing behind it, every page load failed, and no status ever arrived to explain why. That is the state that looked like a reset session.

**It came back in the wrong state.** The extension routed the browser through the backend the moment the backend announced its port, which switched the tailnet back on for anyone who had switched it off, and pointed the browser into a backend that was still stopped. The backend's preferences are on disk and remember what the profile was left in; a freshly started worker remembers nothing, so it follows the backend now — unless you have just asked for something the backend has not reached yet, where your request is the newer fact.

Only `Stopped` means direct browsing, though. The states on the way up — starting, waiting on device approval — keep the browser pointed at the new backend, because the browser holds its proxy setting across a restart of the extension: left to itself it goes on addressing the port the last backend listened on, where nothing answers, and with an exit node configured whatever does get out leaves from this machine's own address instead. The new backend refuses to dial until dialling is safe, which is the failure worth having.

**The popup asked you to install what you already had.** A dead port and a missing backend look identical from inside the extension. Now that the extension remembers having talked to one, it says "Reconnecting…" instead, and only falls back to printing the install command once the reconnects keep failing.

## The extension could come up having done nothing at all

The profile id — the string that names this profile's Tailscale state directory — is read out of extension storage on startup, and everything else waits behind that read: it is what the backend is handed in the init that makes it start Tailscale at all.

Storage does not always answer. When the browser is tearing the extension's worker down around the call it fails the call instead, with nothing where the result should be, and reading a field off that nothing threw. The throw took the rest of the callback with it — including the init. The backend then sat there, started but never told to do anything, sending no status; the popup, having nothing to render, showed a blank line under a toggle that still looked switched on. It read as the popup being slow, and it was really the extension having quietly done nothing since it loaded.

This was there long before this release; the error only names the field that happens to be read first. Now a refusal is retried rather than fatal, every message from a backend is another chance at the read, and an id that storage would not keep is thrown away rather than used — using it would mean a different state directory on the next start, which is a new machine on the tailnet, logged out, with the old one's state stranded on disk. The popup also has something to say for a status that carries nothing: "Connecting…", rather than an empty panel.

## The toolbar button was slow to answer

Two things were making the extension's own button sluggish, and both were work nobody had asked for.

**The backend sent a status per bus notification.** Tailscale's bus fires for anything that happens on the tailnet — peers coming and going, a reissued netmap — and most of it does not change a word of what the extension is shown. Every repeat cost the backend two round-trips to its own local API to rebuild the peer list, and cost the extension a redraw of the toolbar icon: four PNGs fetched and decoded, on the button being clicked. Identical statuses are now dropped before they reach the pipe, and the extension no longer asks the browser to draw an icon it is already showing. A request still always gets an answer, changed or not.

**The popup waited on the background to say anything at all.** It has its own
copy of the last status now, kept in extension storage, so it paints what was
last true the moment it opens and keeps its spinner until the background
confirms or corrects it. Where it used to sit blank for as long as a backend
took to start, it now shows the state it knew and settles. It also stopped
freezing when two of them are open: the background held a single popup
connection, so opening the panel while `popup.html` was also open in a tab left
the tab showing an exit node that had since been changed.

**The worker was left free to be discarded.** The browser throws an idle extension worker away after about thirty seconds, and the native backend is its child process: it dies too, so the next click paid for a whole new process starting Tailscale from cold. While a backend is connected the extension now speaks to it inside that window, which is what keeps the worker resident. It is a deliberate trade — a resident worker for as long as the tailnet is up — and the honest one for a VPN, which is not much use if it has to be restarted every time it is looked at.

## The backend went deaf after a sleep

The native host reads everything it knows about the tailnet — state, netmap, preferences, login URLs — from one watch on Tailscale's IPN bus. Sleep breaks that watch. The read then failed once and the goroutine ended for good: the process stayed up knowing nothing, the popup froze on whatever it had last said, and nothing short of restarting the browser fixed it.

The watch is re-established now, backing off up to thirty seconds so a backend that is genuinely gone is not hammered. Its reconnect loop is covered by a test that breaks a watch, fails the first attempt to rebuild it, and checks the next one is read.

## Two error branches that could never run

The extension checked `procRunning.errror` for a field the backend spells `error`, so a backend reporting that it failed to start was ignored entirely, and the neighbouring branch logged `undefined` in place of the reason an init had failed. Both read the right field now, and both are tested.

## New permissions

`alarms` and `idle`, in both extensions. Neither shows a permission warning; the background script throws on load without them, which is why the extension has to be reloaded rather than just updated in place.

## Tested end to end for the first time

Everything here was covered by tests that mock the browser, and mocks are
exactly where these bugs were invisible: a native port that is the same object
on every connect, storage that always answers, timers that fire only when a
test says so, and a worker that is never discarded.

`tests/e2e.test.mjs` loads the extension into Chromium, registers a stand-in
backend that speaks the same protocol as the Go one, kills it, and checks that
the extension brings another back, initialises it under the same profile id,
and routes the browser through it again — the sequence a sleeping laptop
produces, run in a real browser.

## Known limitations

- **Firefox has still not been run live.** Its test suite passes and it is exercised against a mocked browser API on every commit — including everything above — but nobody has loaded it through `about:debugging`.
- **Losing the backend still hands the browser a direct connection.** When the native messaging host goes away, the extension resets the browser proxy to direct rather than leaving it pointed at a dead port. The window is shorter now, because the reconnect starts a second later instead of whenever someone notices, but making it fail closed would mean pages stop loading entirely whenever the backend dies, and has not been done.
- **Windows cannot register the native host.** The binary builds, but there is no registry install path yet.
